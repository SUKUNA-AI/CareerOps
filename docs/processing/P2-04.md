# P2-04 — Requirements + ResumeEvidence

P2-04 строит две воспроизводимые семантические проекции нормализованных данных:

```text
NormalizedVacancy
→ RequirementSet

NormalizedResume
→ ResumeEvidenceSet
```

P2-04 не решает, подходит ли резюме вакансии, не выбирает доказательства для конкретного требования и не считает итоговый score.

## Граница ответственности

P2-03 выполняется раньше P2-04 и возвращает только:

```text
KEEP
EXCLUDE_PROVEN
```

`EXCLUDE_PROVEN` завершает обработку пары до P2-04.

`KEEP` означает только отсутствие доказанного жёсткого исключения. После `KEEP` Processing получает или строит `RequirementSet` и `ResumeEvidenceSet`, а затем публикует `P204ResultArtifact` для конкретной пары vacancy × resume.

## RequirementSet

`RequirementSet` хранит дерево требований вакансии, а не плоский список слов.

Для одного атомарного `Requirement` сохраняются:

- `subjects`
- `activity`
- `context`
- `importance`
- `modality`
- `polarity`
- `threshold`
- `source_refs`

Поддерживаются логические узлы:

- `ALL`
- `ANY`
- `CONDITIONAL`

Модальность различает:

- `REQUIRED`
- `PREFERRED`
- `OPTIONAL`
- `NOT_REQUIRED`
- `PROHIBITED`
- `UNKNOWN`

Пример:

```text
Python или Scala
SQL
ETL от 3 лет
```

может быть представлен как:

```text
ALL
├── ANY
│   ├── Python
│   └── Scala
├── SQL
└── ETL >= 3y
```

`CONDITIONAL` всегда содержит условие и ровно одного логического потомка. `ANY` содержит не меньше двух потомков. Каждый атомарный requirement принадлежит ровно одному узлу дерева, каждый non-root group имеет ровно одного родителя, а root всегда использует `ALL`.

## Требование к технологии с порогом опыта

Порог опыта не меняет вид требования автоматически.

Фраза:

```text
Python или Scala, опыт от 3 лет
```

означает:

```text
ANY
├── RequirementKind.TECHNOLOGY subject=Python threshold=EXPERIENCE_YEARS >= 3
└── RequirementKind.TECHNOLOGY subject=Scala  threshold=EXPERIENCE_YEARS >= 3
```

Самостоятельная фраза:

```text
Опыт от 3 лет
```

становится `RequirementKind.EXPERIENCE`.

Это разделение важно для P2-06: threshold описывает числовое условие, но не заменяет смысл самого requirement.

## Структурированные поля вакансии

P2-04 использует не только текст вакансии. Более надёжные структурированные поля `NormalizedVacancy` сохраняются напрямую:

- `experience`
- `key_skills`
- `employment`
- `schedules`
- `work_formats`
- `location`
- `relocation_facts`

`professional_roles`, salary, lifecycle flags и timestamps не превращаются в candidate requirements автоматически. Они остаются нормализованными исходными фактами и используются только стадиями, которым действительно нужны.

### ExperienceRange

HH experience category может содержать диапазон, например `1–3 years`, но верхняя граница такой категории не означает «кандидат с опытом больше трёх лет не подходит».

Поэтому P2-04 использует `minimum_years` как нижний qualification threshold и не превращает `maximum_years` HH category в жёсткий upper bound кандидата.

Исходный `source_code` и текстовое представление сохраняются через provenance.

## NOT_REQUIRED и PROHIBITED

Фраза:

```text
Kubernetes не требуется
```

не является запретом и не означает отрицательное требование к кандидату. Она получает:

```text
importance = OPTIONAL
modality = NOT_REQUIRED
polarity = POSITIVE
```

Настоящий запрет:

```text
Использование X запрещено
```

получает:

```text
importance = MANDATORY
modality = PROHIBITED
polarity = NEGATIVE
```

Эти случаи не смешиваются до P2-06.

## Поиск subject

Короткие названия технологий нельзя искать обычным substring search.

P2-04 проверяет границы идентификаторов и поддерживает небольшой версионируемый набор aliases. В частности:

- `Go` не совпадает с `Django` или `MongoDB`
- `C` не совпадает с `C++`
- `R` не извлекается из произвольного слова
- `.NET` распознаётся в `ASP.NET`
- `C#` может быть распознан через `CSharp`
- поддерживаются `cpp`, `dotnet`, `postgres`, `k8s`

Расширение dictionary-backed aliases должно быть версионированным, чтобы изменение словаря меняло семантическую идентичность результата.

## ResumeEvidenceSet

`ResumeEvidenceSet` сохраняет не только упомянутые технологии, но и характер доказательства.

Для одной `ResumeEvidence` сохраняются:

- `subjects`
- `activity`
- `actor_scope`
- `context`
- `polarity`
- `strength`
- `time_span`
- `source_refs`

Примеры:

```text
Kafka в skill list
→ MENTION

Разработал Kafka consumer
→ SELF + DIRECT

Команда использовала Kafka
→ TEAM

Не работал с Kafka
→ NEGATIVE
```

P2-04 также сохраняет доказательства из:

- headline
- current location
- relocation preference
- business trips preference
- work preferences
- total experience
- experience entries
- projects
- education
- languages

Эти данные остаются evidence. Они не становятся автоматически hard gate или match decision.

## Семантическая идентичность и deduplication

`requirement_id` и `evidence_id` не включают `source_path`, `entry_id` или `block_id`.

Если одна и та же семантическая единица встречается в нескольких местах исходных данных, P2-04 хранит один объект и объединяет его `source_refs`.

Provenance объясняет происхождение семантической единицы, но не определяет её идентичность.

Для requirements отдельно учитывается логическое положение в дереве, чтобы один атомарный requirement не оказался одновременно в разных ветках выражения.

## Один semantic artifact на одну semantic version

`RequirementSet` не пересчитывается для каждого resume.

`ResumeEvidenceSet` не пересчитывается для каждой vacancy.

Идентичность requirement artifact включает:

- source identity вакансии
- `semantic_content_hash`
- normalized schema version
- normalization version
- dictionary version
- `requirement_extraction_version`
- artifact schema version

Идентичность evidence artifact строится аналогично и дополнительно содержит `account_key`.

Постоянный индекс хранится в:

```text
careerops_v2.processing_semantic_artifacts
```

Перед первой сборкой используется PostgreSQL advisory lock для соответствующего `cache_key`.

```text
lock semantic identity
↓
lookup PostgreSQL registry
├── ref найден
│   ↓
│   проверить S3 artifact
│   ├── корректен → переиспользовать
│   └── object отсутствует → детерминированно пересобрать
│                            и потребовать точного совпадения ref
└── ref отсутствует
    ↓
    extract
    ↓
    publish immutable artifact
    ↓
    записать ref в registry
↓
unlock
```

Несколько Processing workers поэтому не выполняют один и тот же extraction параллельно.

S3 хранит сами immutable artifacts. PostgreSQL хранит только семантическую идентичность и `ProcessingArtifactRef`.

## Ошибки semantic artifact

Детерминированные ошибки выделены отдельно от временных ошибок инфраструктуры.

К детерминированным относятся:

- некорректная semantic identity
- конфликт registry identity
- нарушение artifact integrity
- несовпадение результата детерминированной пересборки
- нарушение контракта `RequirementSet` или `ResumeEvidenceSet`

Такая ошибка завершает job как terminal failure.

Ошибки PostgreSQL/S3 transport не маскируются под semantic failure. Они доходят до `ProcessingWorker` и обрабатываются как retryable failure.

## Артефакты

P2-03/P2-04 публикуют:

```text
FILTER_TRACE
REQUIREMENT_SET
RESUME_EVIDENCE_SET
P2_04_RESULT
```

Все artifacts неизменяемы, адресуются по SHA-256 и не используют mutable `latest`.

`P204ResultArtifact` проверяет не только `ProcessingArtifactKind`, но и точную поддерживаемую `schema_version` вложенных refs.

Текущие schema versions:

```text
careerops.processing.requirement-set.v2
careerops.processing.resume-evidence-set.v2
careerops.processing.p2-04-result.v2
```

## Production runtime

`careerops-processing serve` поднимает настоящий worker:

```text
PostgreSQL queue connection
        │
        └── PostgresProcessingJobStore
                │
                ▼
        ProcessingWorker
                │
                ▼
          P204Executor
          ├── S3ProcessingInputLoader
          │     ├── pinned ProcessingInputManifest
          │     ├── pinned NormalizedVacancy
          │     └── pinned NormalizedResume
          ├── P2-03 filter
          ├── P204SemanticArtifactResolver
          │     └── separate PostgreSQL semantic registry connection
          └── ProcessingArtifactPublisher
                └── careerops-artifacts
```

Queue и semantic registry используют разные PostgreSQL connections, потому что heartbeat lease должен работать одновременно с semantic extraction и S3 operations.

`/healthz` показывает liveness процесса.

`/readyz` возвращает `200` только после успешного открытия PostgreSQL/S3 dependencies и сборки `ProcessingWorker`. До этого endpoint возвращает `503`.

## Настройки запуска

До P2-04 сервис не требует Jina или matching-core.

Обязательные внешние зависимости сейчас:

- PostgreSQL
- normalized S3 bucket
- artifacts S3 bucket

`CAREEROPS_PROCESSING_RERANKER_URL` и `CAREEROPS_PROCESSING_MATCHING_CORE_TARGET` не входят в P2-04 config. Они должны появиться только вместе со стадиями, которые реально используют соответствующие сервисы.

## Что не входит в P2-04

P2-04 намеренно не содержит:

- Jina reranking
- evidence selection для конкретного requirement
- `MATCHED / NOT_EVIDENCED / UNKNOWN / CONTRADICTED`
- hard gates финальной квалификации
- score bounds
- `SKIP / REVIEW / APPLICATION_CANDIDATE`

Это ответственность P2-05, P2-06 и P2-07.
