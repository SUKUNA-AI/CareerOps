# P2-08 — Application Owner

P2-08 не решает, подходит ли вакансия конкретному резюме. Единственный владелец match decision — Processing P2-03…P2-07. Application Owner потребляет только текущий `APPLICATION_CANDIDATE` и владеет внешним side effect.

## Граница ответственности

```text
Processing current APPLICATION_CANDIDATE
                │
                ▼
         Application Owner
                │
         precheck / guards
                │
                ▼
       applicant transport facade
                │
                ▼
              HH
```

Application Owner отвечает за:

- account×vacancy idempotency guard;
- проверку, что candidate всё ещё current непосредственно перед submit;
- lease/fencing собственного workflow;
- transport precheck;
- submit outcome classification;
- safe retry только до доказанного/возможного submit;
- reconciliation неизвестного исхода;
- immutable audit events в S3.

Он не пересчитывает score, qualification или Processing policy.

## Permanent submission guard

Уникальный guard имеет scope:

```text
account_id × source_vacancy_id
```

Guard создаётся атомарно с первой application и не удаляется после submit. Он защищает от второго независимого application row и blind duplicate submit.

Permanent guard не означает permanent binding к старому Processing result.

### Безопасный pre-submit rebind

Если application ещё не могла выполнить submit, а её Processing result устарел, тот же application row может быть перевязан к новому current eligible result.

Rebind разрешён только если:

- `submitted_at IS NULL`;
- живого lease нет;
- state является `safe_failure` либо `blocked` с причиной `application.candidate_stale_before_submit`;
- новый current `application_candidate` всё ещё eligible;
- binding/resume/vacancy lifecycle разрешает auto-apply;
- нет более нового активного Processing job;
- account gate открыт.

Guard и `application_id` при этом сохраняются. Новый независимый application не создаётся.

После фактического или потенциального submit automatic rebind запрещён.

## Lease и fencing

Claim создаёт уникальный lease token и `lease_expires_at`.

Все переходы state machine требуют одновременно:

```text
application_id совпадает
lease_token совпадает
lease_expires_at > now()
```

Во время внешнего transport вызова Application Owner продлевает lease heartbeat. Whole-operation deadline обязан быть меньше lease duration.

Если worker теряет lease, старый worker не имеет права зафиксировать новый terminal state.

## Account gate

Account gate различает pre-submit и unresolved post-submit states.

Живые pre-submit states:

```text
preparing
precheck
```

Они блокируют другую account operation пока жив lease.

Unresolved submit states:

```text
submitting
submitted_unconfirmed
uncertain
reconciliation_required
```

Они блокируют новую account operation независимо от наличия lease. Это fail-closed защита от ситуации, когда HTTP/vendor thread пережил worker lease или outcome submit неизвестен.

HH application-limit cooldown является дополнительным account-level gate.

## Precheck

До внешнего submit выполняется transport precheck.

Основные исходы:

```text
ALREADY_SUBMITTED → submitted_confirmed
READY             → повторная current-candidate проверка → submitting
SAFE_FAILURE      → safe_failure + retry schedule
BLOCKED           → blocked
```

Questionnaire/auth/captcha conditions не превращаются в автоматический submit.

После successful precheck candidate проверяется ещё раз непосредственно перед переходом `submitting`. Если Processing result стал stale, submit не вызывается.

## Submit outcomes

```text
ALREADY_SUBMITTED → submitted_confirmed
SUBMITTED         → submitted_unconfirmed
SAFE_FAILURE      → safe_failure
UNCERTAIN         → uncertain
BLOCKED           → blocked
```

Ключевое правило:

> после начала внешнего submit transport ambiguity никогда не превращается в blind retry.

Timeout/connection uncertainty после submit переводит application в `uncertain` и далее в reconciliation.

## Recovery

Expired pre-submit lease (`preparing` / `precheck`) безопасно переводится в retryable pre-submit state.

Expired `submitting` lease означает неизвестный внешний исход:

```text
submitting
→ reconciliation_required
```

Expired reconciliation lease также остаётся `reconciliation_required` и планируется повторно.

Recovery очищает lease, но unresolved state продолжает блокировать новые account submissions через account gate.

## Reconciliation

Reconciliation ищет уже существующий upstream submission по account/vacancy/resume.

Если submission найден:

```text
submitted_confirmed
```

Если не найден или lookup временно не дал доказательства отсутствия:

```text
reconciliation_required
→ schedule next reconciliation
```

Отрицательный lookup не является разрешением на новый submit.

## Fairness

Worker не может бесконечно обслуживать только reconciliation backlog. После ограниченного burst reconciliation iterations он обязан дать шанс новой eligible application.

Размер burst является operational setting и не меняет business semantics.

## S3 audit

Precheck, submit, stale-before-submit и reconciliation публикуют audit events в SeaweedFS S3.

PostgreSQL хранит URI текущего evidence/audit state, но не заменяет immutable audit layer.

Application Owner readiness требует доступного PostgreSQL control plane и доступного S3 audit bucket. Временная недоступность HH не превращает service readiness в false: transport outcome классифицируется внутри job state machine.

## Vendor boundary

`hh-applicant-tool` является vendored implementation island.

CareerOPS не импортирует его бизнес-логику в Application Owner. Собственный `HHApplicantTransport` facade переводит vendor exceptions/results в стабильные состояния CareerOPS.

Внутренние vendor tests не смешиваются с CareerOPS suite.

## Проверяемые safety properties

Pre-deploy test gates должны доказывать как минимум:

- два workers не claim'ят один account×vacancy одновременно;
- permanent guard создаётся атомарно;
- stale candidate не проходит precheck→submit boundary;
- stale pre-submit application может rebind к current Processing result без второго guard;
- expired lease не может зафиксировать state transition;
- uncertain/reconciliation state блокирует новую account operation;
- submit ambiguity не становится safe retry;
- recovery повторяем и не приводит к blind submit;
- real PostgreSQL locking/constraints участвуют в проверке, а не только SQL string assertions;
- audit events реально записываются в S3-compatible SeaweedFS.
