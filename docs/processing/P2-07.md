# P2-07 — deterministic scoring and policy decision

P2-07 превращает qualification P2-06 и зафиксированную target policy в воспроизводимое решение для пары vacancy × binding.

```text
P2_06_RESULT
RequirementQualificationSet
NormalizedVacancy
TargetPolicy
        │
        ▼
      P2-07
        │
        ├── MatchDecision artifact
        ├── P2_07_RESULT artifact
        └── fenced PostgreSQL current projection
```

P2-07 не отправляет отклик. `APPLICATION_CANDIDATE` является только handoff-кандидатом для будущего Application Owner.

## Решения

P2-07 возвращает ровно одно состояние:

```text
SKIP
REVIEW
APPLICATION_CANDIDATE
```

`REVIEW` не является generic fallback. Оно используется, когда доступные lower/upper bounds действительно допускают разные итоговые решения или когда calibration/scoring signal ещё не позволяет безопасно автоматизировать решение.

## Score bounds

Итоговый score хранится как `ScoreBounds(lower, upper)` в диапазоне `0..100`.

Это ranking/utility interval, а не probability.

`deterministic_score` всегда равен conservative lower bound:

```text
deterministic_score = score.lower
```

Ни midpoint, ни Jina relevance score не используются как итоговая confidence probability.

## Non-compensable hard contradictions

`MANDATORY` и hard criticality не считаются синонимами.

Обычный `REQUIRED/MANDATORY` contradiction влияет на `mandatory_coverage` и после calibration проходит через versioned `mandatory_min_support`. До calibration такой случай остаётся `REVIEW`, а не получает незапиненный hard gate.

Текущий контракт умеет однозначно выразить hard prohibition через modality `PROHIBITED`. Доказанное нарушение такого requirement является non-compensable blocker:

```text
PROHIBITED + CONTRADICTED
        ↓
      SKIP
```

Если позже появится отдельная first-class criticality-модель, она должна быть добавлена в versioned requirement/policy contracts, а не выводиться молча из `MANDATORY`.

## Semantic scoring units

P2-07 строит scoring units из логической структуры requirements.

Для `ALL` независимые requirement/group units учитываются отдельно.

`ANY` и `CONDITIONAL` представлены как composite unit, чтобы альтернативы внутри одной логической группы не увеличивали вес вакансии только из-за количества формулировок.

Из qualification bounds формируются explainable компоненты:

- `mandatory_coverage`
- `preferred_coverage`
- `optional_coverage`
- `technology_fit`
- `responsibility_fit`
- `experience_fit`
- `domain_fit`
- `education_fit`
- `language_fit`
- `work_condition_fit`
- `other_fit`

Каждый компонент хранит lower, upper и policy weight.

## Structured compatibility components

P2-07 также может использовать зафиксированные structured fields `NormalizedVacancy`, не превращая admission `KEEP` из P2-03 в положительный match signal.

Текущие first-class structured components:

- `role_fit`
- `seniority_fit`
- `work_format_fit`
- `location_fit`

Для known deterministic compatibility компонент может быть `[100,100]` или `[0,0]`.

Если structured input недостаточен или неоднозначен, компонент остаётся `[0,100]`.

Remote work учитывается как удовлетворяющий location constraint, когда target policy допускает соответствующий structured path.

## Missing weighted signals

Calibrated policy не имеет права бесплатно перераспределять вес отсутствующего сигнала на остальные компоненты.

Если `ScoringPolicy.component_weights` задаёт положительный вес компоненту, но для exact input этот компонент нельзя построить, P2-07 материализует его как:

```text
[0,100]
```

с исходным policy weight.

Так отсутствие role/seniority/domain или другого ожидаемого сигнала сохраняется как uncertainty и может привести к `REVIEW`, но не повышает conservative score за счёт перенормировки denominator.

## Calibration cutover

Пока manifest содержит:

```text
calibration_version = calibration-unset
```

P2-07 не имеет права выпускать `APPLICATION_CANDIDATE`.

Допустимое поведение до calibration:

- доказанное нарушение `PROHIBITED` → `SKIP`;
- остальные случаи → `REVIEW`.

Это намеренный fail-closed режим: thresholds и weights не угадываются до Gold Set/calibration.

После calibration manifest обязан ссылаться на конкретную `calibration_version`, а `TargetPolicy.scoring` обязан содержать ту же версию.

Несовпадение calibration versions является deterministic configuration error.

## ScoringPolicy

Versioned scoring section содержит:

- `schema_version`;
- `calibration_version`;
- `candidate_min_score`;
- `mandatory_min_support`;
- `component_weights`;
- `candidate_ttl_seconds`.

Weights должны ссылаться только на поддерживаемые scoring components и содержать хотя бы один положительный вес.

Итоговый lower/upper score вычисляется как нормализованная weighted aggregation. Все положительно взвешенные policy signals участвуют в denominator; отсутствующий сигнал представлен uncertainty bounds, а не удаляется из формулы.

## Decision bounds

После calibration:

```text
mandatory.upper < threshold
OR score.upper < candidate threshold
        ↓
      SKIP
```

Если даже лучший допустимый исход не проходит policy, review не нужен.

```text
mandatory.lower >= threshold
AND score.lower >= candidate threshold
        ↓
APPLICATION_CANDIDATE
```

Если даже conservative lower bound проходит policy, решение достаточно определено для handoff.

Во всех остальных случаях bounds пересекают decision boundary:

```text
REVIEW
```

## MatchDecision artifact

`MatchDecisionBundle` фиксирует:

- `input_fingerprint`;
- SHA-256 exact `RequirementQualificationSet`, если он существует;
- `scoring_version`;
- `calibration_version`;
- `policy_version`;
- decision;
- score bounds;
- deterministic score;
- полный component trace;
- critical conflict requirement ids;
- unknown requirement ids;
- not-evidenced requirement ids;
- reason codes.

Контракт запрещает duplicate scoring component keys, пересекающиеся requirement-state buckets и duplicate reason codes.

Путь `EXCLUDE_PROVEN` из P2-03 может завершаться P2-07 deterministic `SKIP` без qualification artifact. Это отдельный явный path, а не поддельный P2-06 результат.

## Artifact-first publication

Current PostgreSQL state разрешено менять только после публикации immutable P2-07 artifacts.

```text
compute MatchDecision
        ↓
immutable MatchDecision artifact
        ↓
immutable P2_07_RESULT
        ↓
verify/hash
        ↓
fenced PostgreSQL current publication
```

Разрешён orphan S3 artifact, если PostgreSQL finalization не состоялась.

Запрещён current PostgreSQL success/result, если соответствующий immutable artifact отсутствует.

Deterministic content-addressed integrity/configuration failures переводятся в terminal Processing failure. Transport failures остаются retryable. Потеря lease остаётся отдельным fencing signal и не маскируется под обычную ошибку публикации.

## PostgreSQL current projection

`PostgresMatchPublicationStore` публикует current state только для worker, который всё ещё владеет действующей lease точной processing job identity.

Перед публикацией проверяются:

- vacancy/binding pair;
- job id;
- input fingerprint;
- lease token;
- status `running`;
- неистёкшая lease;
- P2-07 artifact kind/schema.

Используется тот же pair advisory lock, что и reconciliation path.

Mapping решения в current `match_results`:

```text
APPLICATION_CANDIDATE → eligible
REVIEW                → review
SKIP                  → rejected
```

Только `APPLICATION_CANDIDATE` создаёт/активирует запись в `application_candidates` с versioned/calibrated TTL.

`REVIEW` и `SKIP` withdraw существующий application candidate.

## Stale-output fencing

Migration `20260910_v2_0006_processing_output_fencing` и queue publication path гарантируют, что старый результат не остаётся current после изменения desired identity.

Покрытые сценарии:

- expired/stale lease не может публиковать current result;
- новая superseding job инвалидирует старый match result и withdraw candidate;
- reconciliation cancellation после artifact/current publication инвалидирует старый output;
- explicit pair withdrawal удаляет current `match_results` и withdraw candidate даже если предыдущая processing job уже `succeeded` и active job больше нет.

Таким образом current state принадлежит только актуальной vacancy × binding identity.

## Application Owner boundary

P2-07 заканчивается на:

```text
APPLICATION_CANDIDATE
```

Он не проверяет финальные внешние условия отправки и не выполняет application action.

Будущий Application Owner отдельно владеет:

- binding/resume selection;
- `auto_apply` policy;
- quota/rate guard;
- freshness;
- source/UI state;
- idempotency отправки;
- channel-specific application mechanics.

Processing не должен забирать эту ответственность обратно.

## Gold Set и release gate

Код, contracts, replay/fencing и execution path P2-07 реализованы, но production calibration намеренно не выдумана.

Gold Set должен определить как минимум:

- Evidence Recall@K и рабочий Jina `top_k`;
- token budget;
- calibration bands;
- `mandatory_min_support`;
- component weights;
- candidate threshold;
- REVIEW band.

Поэтому `calibration-unset` остаётся корректным production-safe состоянием до отдельной calibration работы. Формальный release gate автоматического `APPLICATION_CANDIDATE` не считается пройденным, пока нет versioned Gold Set/calibration.

## Replay

Replay P2-07 использует зафиксированные:

- exact P2-06 qualification artifact;
- normalized vacancy input;
- target policy version;
- scoring version;
- calibration version.

Jina повторно вызывать для P2-07 не требуется: его relevance output уже был зафиксирован upstream в P2-05, а qualification — в P2-06.
