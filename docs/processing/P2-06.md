# P2-06 — deterministic requirement qualification

P2-06 превращает зафиксированные semantic inputs P2-04 и ranked candidate selection P2-05 в детерминированную qualification по каждому requirement.

```text
RequirementSet
ResumeEvidenceSet
EvidenceCandidateSet
        │
        ▼
      P2-06
        │
        ▼
RequirementQualificationSet
        │
        ▼
   P2_06_RESULT
```

P2-06 не считает итоговый match score и не принимает application decision.

## Граница ответственности

P2-05 отвечает только за relevance/ranking evidence. P2-06 отвечает за смысловую квалификацию evidence относительно requirement.

Для каждого applicable requirement P2-06 возвращает ровно одно состояние:

```text
MATCHED
NOT_EVIDENCED
UNKNOWN
CONTRADICTED
```

Эти состояния не являются вероятностями и не вычисляются порогом по Jina relevance score.

Низкий Jina score сам по себе никогда не означает `CONTRADICTED`.

## Candidate boundary

P2-06 выполняет actor/polarity/scope/duration qualification только по `EvidenceCandidate` из ranked selection P2-05.

`pool_evidence_ids` используется для проверки provenance и полноты pre-Jina evidence search, но evidence, которое не было выбрано Jina в ranked candidates, не может молча создать `MATCHED` или `CONTRADICTED` в обход P2-05.

```text
ResumeEvidenceSet
        ↓
P2-05 candidate pool
        ↓
Jina top-k
        ↓
selected EvidenceCandidate[]
        ↓
P2-06 qualification
```

Полнота имеет два независимых уровня:

1. pre-Jina pool должен покрывать весь `ResumeEvidenceSet`;
2. ranked selection должна быть exhaustive относительно этого pool, если P2-06 хочет доказать отсутствие evidence.

Поэтому полный pre-Jina pool сам по себе недостаточен для `NOT_EVIDENCED`. Если `top_k < |pool|` и среди выбранных candidates нет decisive support/contradiction, P2-06 возвращает `UNKNOWN` с `evidence.selection_incomplete`: нужное evidence могло остаться в отрезанном хвосте reranking.

При этом decisive evidence, реально попавшее в selected candidates, по-прежнему может доказать `MATCHED` или `CONTRADICTED` даже при truncated tail. Ограничение относится именно к отрицательному выводу из отсутствия доказательства.

Любая ссылка P2-05 на несуществующий `ResumeEvidence.evidence_id` является deterministic contract error, а не semantic outcome.

## Support bounds

Каждая qualification содержит `SupportBounds(lower, upper)` в диапазоне `0..1`.

Текущая детерминированная семантика:

- `MATCHED` → `[1, 1]`
- `CONTRADICTED` → `[0, 0]`
- `NOT_EVIDENCED` → `[0, 1]`
- `UNKNOWN` → `[0, 1]`

`NOT_EVIDENCED` и `UNKNOWN` сохраняют неопределённость. Они не являются отрицательной вероятностью и не должны автоматически превращаться в `SKIP`.

## Alignment

Qualification сначала определяет, относится ли выбранное evidence к requirement.

Приоритет subject alignment:

1. одинаковый `dictionary_key`, если он зафиксирован;
2. иначе одинаковый normalized subject;
3. если requirement не имеет subjects, допускается exact activity alignment.

Lexical similarity и Jina score не заменяют semantic identity.

## Actor scope и evidence strength

Доказательным actor scope считается:

- `SELF`;
- `PROJECT` только для technology/responsibility requirement и project context.

Доказательной strength считается:

- `DIRECT`;
- `SUPPORTED`.

Team-level, слабое или иным образом недоказательное evidence может быть релевантным, но не превращается автоматически в `MATCHED`. Такой случай остаётся `UNKNOWN`, если он не разрешается более сильным evidence.

## Polarity и contradiction

Для aligned decisive evidence:

- одинаковая polarity с requirement → supporting evidence;
- противоположная polarity → contradicting evidence.

Если присутствует только supporting decisive evidence, requirement может стать `MATCHED`.

Если присутствует только contradicting decisive evidence, requirement становится `CONTRADICTED`.

Если одновременно присутствуют decisive support и contradiction, P2-06 не выбирает удобный источник и возвращает:

```text
UNKNOWN
reason = requirements.source_conflict
```

Это сохраняет конфликт данных для последующего review/replay.

## NOT_EVIDENCED против UNKNOWN

`NOT_EVIDENCED` является более сильным утверждением, чем «в top-k ничего не нашли».

Он допустим только в двух случаях:

- `ResumeEvidenceSet` действительно пуст;
- P2-05 использовал полный pre-Jina pool, а selected candidates исчерпывают этот pool, после чего semantic support для понятного subject/activity requirement не найден.

Если pre-Jina pool неполный или Jina top-k отрезал часть полного pool, отсутствие aligned selected evidence означает:

```text
UNKNOWN
reason = evidence.selection_incomplete
```

Если exhaustive selection выполнена и semantic support отсутствует, допускается:

```text
NOT_EVIDENCED
reason = requirements.subject_not_evidenced
```

Если semantic alignment невозможно доказать детерминированно, состояние остаётся `UNKNOWN`.

Пустой `ResumeEvidenceSet` фиксируется как `NOT_EVIDENCED`, а не как contradiction.

## Experience thresholds

Для `RequirementThresholdMetric.EXPERIENCE_YEARS` P2-06 считает подтверждённую длительность только по aligned supporting selected evidence.

Правила:

- пересекающиеся периоды объединяются;
- active period заканчивается в manifest `as_of`;
- одинаковый период не суммируется дважды;
- неполные даты сохраняют uncertainty;
- недостаточно подтверждённых лет → `NOT_EVIDENCED`, а не `CONTRADICTED`;
- если из-за неполных дат невозможно доказать threshold → `UNKNOWN`.

Для отрицательного threshold-вывода действует то же правило полноты selection: если релевантный evidence tail мог быть отсечён top-k, недостаточная длительность не считается доказанной окончательно.

`as_of` является частью зафиксированного input manifest, поэтому duration replay не зависит от текущей даты выполнения.

## Requirement groups

P2-06 сохраняет логическую структуру `RequirementSet`.

Для support bounds групп:

```text
ALL → min(children)
ANY → max(children)
```

То есть для `ALL` итог ограничен самым слабым обязательным членом, а для `ANY` достаточно наиболее поддержанного допустимого варианта.

`CONDITIONAL` без разрешённого условия не угадывается и остаётся `[0,1]` с `requirements.condition_unresolved`.

`NOT_REQUIRED` requirements не квалифицируются как обязательные evidence checks и считаются нейтральными для групповой агрегации.

## RequirementQualificationSet

Artifact фиксирует:

- `input_fingerprint`;
- SHA-256 exact `RequirementSet`;
- SHA-256 exact `ResumeEvidenceSet`;
- SHA-256 exact `EvidenceCandidateSet`;
- `qualification_version`;
- qualification каждого applicable requirement;
- group support bounds;
- ignored `NOT_REQUIRED` requirement ids.

Для каждого requirement сохраняются ranked/supporting/contradicting/ambiguous evidence ids и reason codes. Это позволяет объяснить решение без повторного model call.

## Artifact boundary

Порядок публикации остаётся artifact-first:

```text
compute RequirementQualificationSet
        ↓
immutable S3 write
        ↓
verify/hash
        ↓
publish P2_06_RESULT
        ↓
P2-07 может продолжать
```

PostgreSQL не заменяет immutable qualification artifact.

## Ошибки и fail-closed behavior

P2-06 завершает job детерминированной ошибкой при несовместимых input identities, отсутствующих required selections, dangling evidence ids или нарушенном artifact contract.

Он не имеет права преобразовывать protocol/data errors в `NOT_EVIDENCED` или `CONTRADICTED`.

## Выход в P2-07

P2-07 получает уже квалифицированную структуру:

```text
RequirementSet
RequirementQualificationSet
NormalizedVacancy structured fields
TargetPolicy
```

P2-07 не должен повторно интерпретировать Jina scores. Он использует qualification states/support bounds и структурированные compatibility signals для итоговой policy decision.
