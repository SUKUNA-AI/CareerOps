# Processing v2 — P2-03 deterministic high-recall filter

P2-03 — детерминированный admission filter внутри `careerops_processing.core`

Его задача не определить, подходит ли вакансия окончательно, а безопасно убрать только те варианты, для которых несовместимость уже доказана

Главный принцип:

```text
несовместимость доказана
↓
EXCLUDE_PROVEN

всё остальное
↓
KEEP
```

## Семантика результата

Фильтр возвращает только два результата:

- `KEEP` — безопасное исключение не доказано
- `EXCLUDE_PROVEN` — доказано одно или несколько явных несовместимых условий

`KEEP` не является match decision

Он не означает, что вакансия подходит, имеет высокий score или должна стать application candidate

После `KEEP` вакансия продолжает движение по Processing pipeline

## Fail-open правило

P2-03 намеренно работает fail-open при недостатке информации

Вакансия остаётся `KEEP`, если данные:

- отсутствуют
- неоднозначны
- частично разобраны
- содержат смешанные роли
- не позволяют однозначно определить work format
- не позволяют доказать location conflict
- не позволяют сравнить experience

Unknown не превращается в отрицательный факт

Низкая уверенность не является основанием для исключения

## Что может дать EXCLUDE_PROVEN

Текущая реализация умеет доказать следующие группы hard exclusion:

- вакансия явно архивирована или закрыта для откликов
- primary role явно не пересекается с разрешёнными ролями `TargetPolicy`
- primary role целиком относится к явно запрещённым ролям
- seniority явно входит в запрещённый набор
- management context явно запрещён policy
- известный work format не пересекается с разрешёнными форматами
- известная location явно конфликтует с policy и remote alternative отсутствует
- релокация явно обязательна при policy, запрещающей релокацию
- известный разрыв по experience превышает разрешённый предел
- найден явно запрещённый context без отрицания

Каждое доказанное исключение содержит:

```text
rule_id
reason_code
policy_version
source-backed evidence
```

То есть решение можно объяснить и воспроизвести на том же `TargetPolicy`

## Primary role и incidental technology

Упоминание технологии не считается профессией само по себе

Например:

```text
Data Engineer, Java stack
```

не превращается автоматически в Java Backend

Для `EXCLUDE_PROVEN` title должен явно доказывать чужую role family

Поэтому общие слова вроде языка, framework, platform или research context сами по себе недостаточны

## Seniority и management

`Senior`, `Lead` или другой уровень не является универсальным blocker

Исключение возможно только если соответствующий уровень или management context запрещён конкретным `TargetPolicy`

Это позволяет разным target иметь разные допустимые диапазоны

## Work format и location

География не рассматривается отдельно от work format

Если вакансия допускает remote и policy допускает remote, местоположение работодателя само по себе не доказывает конфликт

Неизвестный или неразобранный work format также не позволяет доказать geography rejection

Пример:

```text
работодатель: Санкт-Петербург
формат: remote
policy: Москва или remote
```

Результат должен оставаться `KEEP`

## Relocation и отрицание

Фильтр различает явное требование релокации и отрицание такого требования

Например:

```text
relocation required
```

может доказать blocker

А:

```text
relocation not required
```

не может быть интерпретировано как требование переезда

## Experience

Experience gap проверяется только когда известны обе стороны:

- minimum experience вакансии
- experience кандидата

Если одна из сторон неизвестна, фильтр оставляет `KEEP`

Отсутствующее значение не подменяется нулём

## Forbidden context и отрицание

Configured forbidden context считается доказанным только при ненегированном упоминании

Например:

```text
We build gambling products
```

может доказать exclusion при соответствующей policy

Но:

```text
We do not work with gambling products
```

не должно приводить к исключению

## Где проходит граница P2-03

P2-03 не выполняет:

- semantic requirement extraction
- evidence ranking через Jina
- qualification requirement × evidence
- финальный score
- `APPLICATION_CANDIDATE` decision
- отправку отклика

Эти задачи принадлежат следующим этапам Processing

```text
P2-03
high-recall filter
↓
P2-04
Requirement / RequirementGroup / ResumeEvidence
↓
P2-05
Jina evidence ranking
↓
P2-06
MATCHED / NOT_EVIDENCED / UNKNOWN / CONTRADICTED
↓
P2-07
SKIP / REVIEW / APPLICATION_CANDIDATE
```

## Эталонная реализация

Текущая Python-реализация в `careerops_processing.core` является эталоном корректности P2-03

C++ matching-core может забирать измеренные deterministic hot paths только после parity tests, доказывающих эквивалентную семантику

Оптимизация не должна менять fail-open поведение фильтра
