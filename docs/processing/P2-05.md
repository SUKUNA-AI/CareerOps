# P2-05 — Jina evidence candidate selection

P2-05 сокращает `ResumeEvidenceSet` до небольшого ранжированного набора evidence-кандидатов для каждого атомарного `Requirement`.

```text
P2_04_RESULT
├── RequirementSet
└── ResumeEvidenceSet
        ↓
P2-05
        ↓
EvidenceCandidateSet
        ↓
P2_05_RESULT
```

P2-05 не принимает qualification decision и не считает итоговый match score.

## Граница ответственности

Для каждого requirement P2-05 строит детерминированный query и детерминированные documents из `ResumeEvidence`, затем передаёт их отдельному Jina reranker runtime.

Jina может вернуть только порядок evidence и relevance score.

Jina не имеет права возвращать или определять:

- `MATCHED`
- `NOT_EVIDENCED`
- `UNKNOWN`
- `CONTRADICTED`
- hard gate
- итоговый score
- `APPLICATION_CANDIDATE`
- решение об отклике

Эта семантика принадлежит P2-06/P2-07.

## Candidate pool

P2-05 использует high-recall pool: для обычного requirement в Jina передаётся весь `ResumeEvidenceSet`.

До reranker не применяется lexical/cosine prefilter, который мог бы потерять нужное evidence.

`NOT_REQUIRED` requirements не требуют доказательства соответствия и не отправляются в Jina. Для них фиксируется `SKIPPED_NOT_REQUIRED`.

Если `ResumeEvidenceSet` пустой, фиксируется `NO_EVIDENCE` без вызова Jina.

## EvidenceCandidateSet

`EvidenceCandidateSet` содержит:

- `input_fingerprint`
- SHA-256 точного `RequirementSet`
- SHA-256 точного `ResumeEvidenceSet`
- полный `JinaVersionBundle`
- результат для каждого requirement

Для одного requirement сохраняются:

- `requirement_id`
- `state`
- exact rendered `query_text`
- полный ordered `pool_evidence_ids`
- SHA-256 rendered candidate pool
- `top_k` выбранных `evidence_id`
- rank
- relevance score

Relevance score является только выходом reranker и не является qualification score.

## Детерминированный rendering

Rendering не включает provenance (`source_path`, `block_id`, `entry_id`) и не должен меняться при переносе одной semantic unit между источниками.

Изменение формата query/document требует новой `rendering_version`.

Изменение правил выбора candidate pool, `top_k` или post-processing требует новой `selection_version`.

## JinaVersionBundle

Каждый новый P2-05 manifest обязан pin'ить:

- `model_id`
- `model_revision`
- `model_code_revision`
- `tokenizer_revision`
- `runtime_backend`
- `dtype_or_quantization`
- фактическую `torch_version`
- фактическую `transformers_version`
- `rendering_version`
- `selection_version`
- `block_protocol`
- `token_budget`
- `top_k`

Model/code/tokenizer revisions определяют загружаемые Hugging Face artifacts.

`torch_version` и `transformers_version` нельзя брать на доверии из env GPU-сервиса. `careerops-reranker` получает их из metadata реально установленных Python distributions и возвращает в runtime identity.

Processing отправляет ожидаемую runtime identity из manifest в каждый `/v1/rerank` request. Несовпадение любой runtime части является protocol error и не допускает публикацию `EvidenceCandidateSet`.

## Manifest cutover P2-04 → P2-05

`ProcessingVersionBundle.jina` остаётся optional на уровне общего manifest contract, потому что исторические P2-04 manifests должны оставаться валидными и воспроизводимыми.

Правила исполнения:

```text
P2-04 manifest
jina = null
→ валиден для P2-03/P2-04 replay
→ P2-05 его не принимает

P2-05 manifest
jina = pinned JinaVersionBundle
→ обязателен для запуска P2-05
```

Новый P2-05 manifest pin'ит Jina до выполнения P2-03. Поэтому `JinaVersionBundle` присутствует даже если пара затем получает `EXCLUDE_PROVEN`.

Для `EXCLUDE_PROVEN` reranker не вызывается, `EvidenceCandidateSet` не создаётся, но итоговая контрольная точка всё равно публикуется как `P2_05_RESULT`.

Это не позволяет текущему runtime молча дообогащать старый P2-04 manifest новой незапиненной зависимостью.

## Отдельный GPU service

PyTorch/Transformers не входят в основной `careerops-processing` runtime.

```text
careerops-processing
      │ HTTP
      ▼
careerops-reranker
      │
      ▼
Jina GPU runtime
```

Так Processing остаётся CPU/control-plane сервисом, а model lifecycle, CUDA и Hugging Face custom code принадлежат отдельному process/container.

Processing использует:

```text
CAREEROPS_PROCESSING_RERANKER_URL
CAREEROPS_PROCESSING_RERANKER_TIMEOUT_SECONDS
CAREEROPS_PROCESSING_RERANKER_UNAVAILABLE_DELAY_SECONDS
```

GPU service использует `CAREEROPS_RERANKER_*` settings из `infra/compose/reranker/env.example`.

## Ошибки

Временная недоступность reranker:

```text
HTTP/network/inference unavailable
→ DEFERRED
→ retry later
```

Детерминированные нарушения:

```text
missing JinaVersionBundle
runtime identity mismatch
invalid response contract
invalid result indices
pinned token budget exceeded
semantic input identity mismatch
→ TERMINAL_FAILURE
```

Reranker outage не должен превращаться в `NO_EVIDENCE`, `NOT_EVIDENCED` или отрицательный match.

## Token budget

Token budget входит в manifest и проверяется до model inference.

Runtime считает токены на exact prompt/block representation, используемом pinned Jina implementation. Если запрос превышает budget, P2-05 не обрезает pool незапиненным эвристическим способом, а завершает работу deterministic error.

Изменение block splitting/truncation protocol требует новой `block_protocol`.

## Выход в P2-06

P2-06 получает только зафиксированные структуры:

```text
RequirementSet
ResumeEvidenceSet
EvidenceCandidateSet
```

Для каждого requirement он видит ordered `evidence_id[]`, но обязан самостоятельно читать соответствующие `ResumeEvidence` и определять qualification state.

P2-05 является selector, а не judge.
